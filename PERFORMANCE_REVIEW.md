# Проверка производительности

11 сентября 2026. Первоначальный аудит и последующая оптимизация локальной Django-сборки.

## Результат оптимизации

Изменения реализованы с сохранением композиции, эффектов и их таймингов. Видео и фотографии
не перекодировались. Повторён тот же сценарий с выключенным кэшем и CPU ×4 / 1,6 Мбит/с.

| Показатель | До | После |
|---|---:|---:|
| Передача первого экрана лендинга без gzip, включая видео | 2,51 МБ | 1,98 МБ (−21%) |
| Передача пустого магазина без gzip | 0,75 МБ | 0,27 МБ (−63%) |
| Логотип в шапке, выбранный браузером файл | 506 201 байт | 33 526 байт (−93%) |
| Самая длинная задача при загрузке лендинга, CPU ×4 | 1 291 мс | 325 мс (−75%) |
| LCP лендинга, mobile | 2,39 с | 2,07 с |
| LCP пустого магазина, mobile | 1,00 с | 0,98 с |
| CLS магазина, mobile, в измеренном сценарии | 0,116 | 0 |
| Сумма сдвигов лендинга без недавнего ввода, mobile | 0,00005 | 0,038 |

Это отдельные лабораторные прогоны, а не статистическая оценка реальных посетителей.
Блокировки полностью не исчезли: остаточная длинная задача 325 мс означает, что слабый телефон
по-прежнему следует проверить отдельно. Выпуск на VPS и его gzip ещё не проверялись;
выигрыш от серверного сжатия в приведённые проценты не включён.

### Что изменено

- Подготовка SplitText и текстовых таймлайнов распределена по отдельным задачам с возможностью
  отрисовки и обработки ввода между секциями. Ближайшая к viewport секция получает приоритет.
  Набор эффектов, параметры и длительности сохранены. Задачи отменяются при уходе со страницы;
  ошибка отложенного эффекта возвращает читаемый исходный текст.
- Убрана инвалидация всех символов при каждом refresh. Динамические значения пересчитываются
  при изменении размеров окна. Загрузки изображений с заранее заданной геометрией больше
  не запускают глобальный пересчёт всех сцен; явные изменения контента по-прежнему обновляют геометрию.
- Подготовлены варианты логотипа 192/384 px и lossless-версия исходного размера.
  `srcset` выбирает подходящий ресурс. Исходные PNG сохранены.
- Фон hero и атрибут `poster` используют один адрес. Исходное видео подключается после
  запуска интерфейса, когда hero виден. При reduced motion, Save-Data и без JS остаётся постер.
- Резервная навигация магазина перенесена в `<noscript>`: включение JS больше не меняет высоту шапки.
- Для публичной статики настроен gzip в `deploy/nginx.conf`. Качество содержимого при gzip не меняется.

### Качество и проверка

- **Видео и фотографии:** исходные файлы, без дополнительной потери качества и изменения разрешения.
- **Полноразмерные WebP логотипов:** encoder проверяет точное совпадение каждого RGBA-пикселя с PNG.
- **Маленький логотип:** это уменьшенная версия, а не пиксельная копия 848×848. Кодирование полученного
  изображения без потерь. Сравнение при 42 CSS px и DPR 1/2/3 сохраняет читаемые детали; различия
  сглаживания есть. Средняя разница RGB-канала — около 8/255, 5/255 и 3/255 соответственно.
  Это техническая разница пикселей, а не «процент потери качества».
- **Первый экран:** текстовый блок hero совпал с исходной React-сборкой на 1440/768/390/320 px:
  ноль отличающихся пикселей при зафиксированном медиа-слое. Это не сравнение всех видеокадров.
- **Поведение:** 10 сценариев проверки лендинга прошли, включая якоря, no-JS, reduced motion,
  очистку сцен и восстановление отраслевой позиции после HTMX/Back.
  Дополнительно сопоставлены промежуточные состояния вводной секции, водной системы и контактов
  на 1440/390 px. Состав символов и типы эффектов совпадают; координаты отдельных символов
  различаются до примерно 4,3 CSS px в выбранных состояниях. Покадровая идентичность всех
  скролл-анимаций не заявляется. Данные: `artifacts/performance-visual/motion-comparison.json`.
- **Магазин и новые ограничения загрузки:** 6 прежних браузерных сценариев и 4 новых прошли:
  стабильность шапки при задержке JS, отсутствие запросов видео при reduced motion/Save-Data,
  уход со страницы во время подготовки сцен.
- **Сервер:** 64 теста, 63 прошли и 1 пропущен на SQLite, поскольку требует PostgreSQL.
  Сборка, синтаксис JS и Ruff прошли.

Повторение: `node scripts/measure-performance.mjs` при работающем Django на порту 8000;
путь результатов задаётся через `PERF_OUTPUT`, по умолчанию `artifacts/performance-after/`.
Изображения воспроизводятся командой `python scripts/encode-brand-assets.py` с зависимостями проекта.
Снимки, сравнения и отчёт анимаций: `artifacts/performance-visual/`.

## Первоначальный вывод, до исправлений

Магазин имеет небольшой собственный JS и отдельную сборку без GSAP/Lenis. Лендинг ощутимо
нагружает главный поток при запуске анимаций на замедленном CPU. До выпуска нужны целевые
оптимизации медиа, запуска сцен и мобильной шапки магазина. Пересматривать визуальную концепцию
или заменять стек по результатам этих измерений оснований нет.

## Методика и границы

- Chromium 1234 из локального Playwright cache, Windows, Django development server, SQLite.
- Desktop: 1440×900, DPR 1, без ограничений сети/CPU. Mobile: 390×844, DPR 2,
  CPU ×4, эмуляция 1,6 Мбит/с и задержки 150 мс через CDP. Кэш выключен.
- Измерены первый экран, ресурсы, длинные задачи, прокрутка лендинга, открытие/закрытие корзины.
  Мобильные загрузки дополнительно повторены с CPU-профилем для проверки найденных причин.
- Сервер отдавал JS/CSS без gzip. Размеры gzip ниже вычислены по файлам и показывают возможный
  размер передачи после настройки сжатия; это не измеренный трафик данного dev-сервера.
- Каталог сейчас пустой. Эти цифры не описывают будущую страницу с реальными фотографиями товаров.
- Это лабораторные наблюдения, не Lighthouse score, не INP реальных посетителей и не нагрузочный тест VPS.
  Замедление CPU не воспроизводит конкретную модель телефона, GPU или Safari.

## Измерения

Размеры передачи ниже в десятичных МБ. Нагрузка первого экрана включает загрузившееся фоновое видео.

| Показатель | Лендинг | Пустой магазин |
|---|---:|---:|
| Первоначальная передача без сжатия JS/CSS | 2,51 МБ | 0,75 МБ |
| Запросы первого экрана | 15 | 10 |
| JS, сумма файлов | 307 449 байт | 155 652 байт |
| JS, вычисленный gzip | 103 142 байта | 46 750 байт |
| CSS, вычисленный gzip | 13 726 байт | 9 667 байт |
| LCP desktop, один прогон | 0,83 с | 0,14 с |
| LCP mobile, первый прогон | 2,39 с | 1,00 с |
| Самая длинная задача mobile при загрузке | 1,29 с | 0,17 с |
| Повторный мобильный прогон с профилем: самая длинная задача | 1,20 с | 0,15 с |

LCP лендинга в этих прогонах — заголовок. Его раннее появление не означает, что закончились
загрузка видео и запуск анимаций. Главный поток занят достаточно долго, чтобы задерживать ввод.
При прокрутке мобильного лендинга также зарегистрированы интервалы кадров более 50 мс.
Частота кадров headless-браузера не используется здесь как обещание FPS на реальном устройстве.

## Проблемы, подтверждённые первоначальным аудитом

1. **Запуск анимаций лендинга — приоритет высокий.** Повторяемые длинные задачи 1,2–1,3 с.
   Профиль показывает значительную работу GSAP с `getComputedStyle` и преобразованиями элементов.
   В `frontend/landing/motion.js` текстовые сцены всех секций разбиваются через SplitText
   и получают таймлайны при старте. Проверить подготовку удалённых секций ближе к viewport,
   объединение пересчётов и повторных `ScrollTrigger.refresh()`, пакетное чтение геометрии.
   Причастность запуска сцен подтверждается профилем; долю каждого механизма предстоит измерить
   после отдельного изменения. Внешний вид, последовательность и характер анимаций сохранять.

2. **PNG-логотип больше, чем требуется для его отображения.** `brand-mark-navy.png` — 506 201 байт,
   а мобильное изображение в шапке магазина занимает 32×32 CSS px. Его передача составляет около
   68% первоначального трафика пустого магазина. Подготовить подходящие размеры и эффективный формат
   с сохранением прозрачности и проверить резкость на DPR 2/3. Большой `brand-lockup-navy.png`
   внизу лендинга также подлежит проверке размера, но загружается лениво.

3. **Мобильная шапка магазина сдвигает контент после запуска JS.** В повторном прогоне `main`
   перемещается с y=119,39 на y=65: около 54 px. Источник — переход от `html:not(.js)`
   с раскрытой навигацией к JS-компоновке. Один этот сдвиг даёт layout-shift 0,116,
   поэтому CLS не может быть ниже этой величины в данном прогоне. Сохранить одинаковую
   начальную геометрию и рабочий режим без JS. Отдельно проверить подмену системного шрифта на Manrope.

4. **Видео и дублирование постера.** WebM — около 1,43 МБ, MP4-альтернатива — около 2,41 МБ.
   Браузер данного теста загрузил только WebM; размеры альтернатив не суммируются.
   На телефоне используется тот же файл 960×540. Проверить отдельное мобильное кодирование и
   поведение при экономии трафика. Постер около 54 КБ загружается дважды по разным URL:
   из `poster` видео и хешированного CSS-фона. Унифицировать адрес при сохранении Safari fallback.

5. **Сжатие на VPS должно быть явным.** В поставляемом `deploy/nginx.conf` нет настройки
   `gzip_types`/Brotli. Глобальная конфигурация реального сервера неизвестна. Включить и проверить
   сжатие HTML/CSS/JS и реальные заголовки ответов; не рассчитывать на него только по числам сборки.

## Что уже помогает

- Раздельные точки входа магазина и лендинга; в магазине нет сцен GSAP и фонового видео.
- Серверный HTML, отсутствие React в рабочей сборке, пагинация каталога.
- WebP/srcset и lazy loading для фотографий ниже первого экрана.
- Остановка hero-видео вне видимой области и при скрытой вкладке, поддержка reduced motion.
- Очистка сцен при HTMX-переходах; в предыдущей функциональной проверке накопления pin/SplitText не обнаружено.
