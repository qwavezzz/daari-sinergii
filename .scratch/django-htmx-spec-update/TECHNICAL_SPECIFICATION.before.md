# Техническое задание: «Дары Синергии»

Версия: 1.1

Дата: 11 сентября 2026 года  
Статус: проект ТЗ для согласования; разработка по этому документу ещё не начата.

## 1. Цель проекта

Разработать серверную часть сайта «Дары Синергии» на Django с PostgreSQL и интернет-магазин на Django Templates, Tailwind CSS, HTMX и Alpine.js. Перенести существующий лендинг с сохранением React, Vite, исходного CSS и анимаций GSAP/Lenis, подключить управляемый контент из Django Admin. Магазин разместить на `shop.dari-sinergii.ru`, оплату реализовать через ЮKassa, развёртывание — через Docker и Nginx.

Новая разработка с нуля относится к серверной части, CMS и магазину. Существующий React-интерфейс лендинга и библиотеки материалов переносится на новую инфраструктуру и адаптируется к серверным данным; повторная вёрстка этих страниц на Django-шаблонах или Tailwind не требуется.

Владелец должен самостоятельно публиковать отзывы, видео, документы и другие предусмотренные материалы, редактировать товары и обрабатывать заказы без изменения кода и повторной загрузки сборки сайта.

### 2.2. Рабочие допущения

Для получения целостного ТЗ ниже приняты следующие исходные решения. Они предложены исполнителем и могут быть изменены при согласовании:

- Один Django-проект с выделенными предметными модулями и одной PostgreSQL-базой обслуживает оба домена: выдаёт HTML-оболочку и данные для React на основном сайте, HTML-страницы и HTMX-фрагменты магазина, административный интерфейс.
- Первая версия — русскоязычный магазин с расчётами в рублях и оформлением заказа без обязательной регистрации.
- Django Admin используется как единая административная панель. Отдельная авторская админка не разрабатывается.
- Корзина и оформление заказа находятся на домене магазина; основной сайт ведёт в каталог или на конкретный товар.
- Отзывы публикует сотрудник через админку. Самостоятельная отправка отзывов посетителями не входит в первую версию.
- В основе оплаты — переход на платёжную страницу ЮKassa и автоматическое подтверждение результата сервером.
- Реальные цены, ассортимент, отзывы, документы и условия продажи предоставляет заказчик.

Открытые бизнес-вопросы перечислены в разделе 17. До их решения нельзя считать соответствующие сценарии готовыми к промышленному запуску. Создание этого ТЗ не означает разрешение на изменение работающего сайта, инфраструктуры или проведение реальных платежей.

Путь к заказу сам по себе не даёт доступа: необходима проверка сессии владельца либо отдельной защищённой ссылки. Публичный идентификатор не является последовательным номером записи базы данных.

Оба домена могут обслуживаться одним развёртыванием. Запросы маршрутизируются по проверенному имени хоста; Nginx передаёт исходный Host, приложение не принимает произвольные домены. Админка и служебные маршруты не должны непреднамеренно дублироваться на основном домене.

Сессия корзины ограничена доменом магазина. Общие cookies для всех поддоменов и междоменные запросы с учётными данными не вводятся без отдельной необходимости.

### 4.3. Организация кода

Рекомендуемое разделение Django-модулей: `content`, `reviews`, `catalog`, `cart`, `orders`, `payments`, `core`. Названия могут уточняться; границы ответственности должны сохраняться.

Основной сайт имеет отдельную фронтенд-сборку React/Vite, магазин — отдельные Django-шаблоны и сборку Tailwind/HTMX/Alpine.js. Они могут находиться в одном репозитории и выпускаться вместе; отдельные сервисы для каждого фронтенда не обязательны.

В магазине Django Templates формирует готовые страницы и HTMX-фрагменты. На основном сайте Django формирует HTML-оболочку с метаданными и начальными данными, а React отображает существующие компоненты. Универсальный REST API для заказов и магазина не требуется. Ограниченный JSON-интерфейс контента нужен для React; Django REST Framework не является обязательной зависимостью.

React и HTMX/Alpine.js не управляют одними и теми же DOM-элементами. На публичных React-страницах не подключаются HTMX/Alpine.js и Tailwind-сброс магазина; на публичных страницах магазина не загружаются React-код лендинга, его глобальный CSS и GSAP/Lenis. Общие шрифты, изображения и логотип могут переиспользоваться без смешивания глобальных стилей.

### 4.4. Подключение React и данных CMS

Рабочая схема первого открытия: **запрос страницы → Django получает опубликованный контент → выдаёт HTML-оболочку, метаданные и безопасный JSON → React отображает существующую страницу**. Основное содержимое передаётся сразу, чтобы не ждать отдельного запроса перед запуском анимированных сцен.

- Vite создаёт production-сборку с manifest; Django подключает соответствующие файлы JS/CSS по manifest, Nginx раздаёт их как статику. Это интеграция сборки с сервером, а не запуск Vite dev-сервера в production. Основа — [документация Vite](https://vite.dev/guide/backend-integration.html).
- Начальные данные передаются как JSON, отделённый от исполняемого кода, например через [Django `json_script`](https://docs.djangoproject.com/en/stable/ref/templates/builtins/#json-script). Они не вставляются строковой конкатенацией в JavaScript или HTML.
- Для переходов React и повторного чтения используются GET-маршруты `/api/content/v1/landing/`, `/api/content/v1/materials/` и `/api/content/v1/materials/<slug>/` на основном домене. Начальные данные и JSON-ответы используют один сервис выборки и один контракт маппинга.
- Контракт содержит только необходимые опубликованные поля, стабильные идентификаторы, порядок, связи, метаданные и URL медиа. В нём фиксируются версия схемы, обязательные поля, пустые значения и форма ошибки. Списки имеют серверные ограничения объёма / пагинацию по необходимости.
- React-компоненты получают редакторские данные через props / слой загрузки. Копии редактируемых текстов и документов в JS не продолжают жить как независимый источник после импорта. Структура сцен и правила вёрстки остаются в коде.
- Публичные GET-ответы не содержат черновики, персональные данные, служебные поля или секреты. Они работают на том же origin, что и React; общие cookies поддоменов и разрешение CORS для всех источников не нужны.
- Предпросмотр черновиков открывается на домене админки в отдельном защищённом представлении с проверкой прав и без публичного кеширования. Для него допускается изолированная оболочка с теми же React-компонентами; публичные JSON-маршруты от этого не начинают выдавать черновики. Cookie админки не расширяется на основной домен.
- Ошибка повторной загрузки не удаляет уже показанный контент: отображается понятное состояние с повтором. Пустая подборка и отсутствие отзывов отличаются от сбоя запроса. При недоступности сервера первого открытия возвращается страница ошибки, а не ложная пустая библиотека.

В базовую архитектуру не входят Next.js и отдельный Node.js-сервер для SSR. Django-оболочка с JSON не является серверным рендерингом React-компонентов. Метаданные и резервное содержимое определены в разделе 11.4; полноценный SSR требует отдельного решения, если понадобится.

## 5. Роли и административная панель

| Роль | Возможности |
|---|---|
| Посетитель | Просмотр сайта, каталога, документов и опубликованных отзывов |

В Django Admin должны быть русские названия разделов и полей, поиск, фильтры, сортировка и понятные сообщения об ошибках. Полномочия проверяются на сервере для каждой операции. Контент-редактор не получает доступ к персональным данным покупателей и настройкам оплаты.

Важные действия журналируются: публикация и снятие с публикации, изменение цены, изменение статуса заказа, операции с платежами и правами доступа. Секреты и платёжные реквизиты карт в журнал не попадают.

## 6. Управление содержимым и отзывы

### 6.1. Контент сайта

Предусмотреть редактирование согласованных заголовков, описаний, контактов, текстов отраслевых направлений и связанных материалов. Структуру сложных анимированных сцен задаёт разработчик; произвольный HTML, JavaScript и редактирование шаблонов через админку не допускаются.

Для документов и видео нужны:

- название, краткое описание, обложка при необходимости;
- файл либо проверенная ссылка на поддерживаемый внешний ресурс;
- тип материала, направление, связь с товаром при необходимости;
- порядок отображения и признак показа на главной;
- состояния «Черновик», «Опубликован», «Архив»;
- дата публикации и сведения об авторе изменения;
- закрытый от посетителей предпросмотр до публикации.

Документ может относиться к нескольким направлениям. Один и тот же файл не требуется загружать отдельно для каждой подборки. Замена файла обновляет все актуальные ссылки; изменение публичного адреса сопровождается сохранением совместимости или перенаправлением.

Для библиотеки сохраняются тематические подборки, фильтрация, краткое описание, открытие и скачивание PDF. Неопубликованные материалы недоступны и по прямой ссылке. Публичная раздача Nginx не должна обходить проверку доступа к черновикам.

Для видео в первой версии рекомендуется ссылка на согласованный видеосервис с обложкой; прямую загрузку допускается включить после определения лимитов и способа хранения. Вставка произвольного iframe-кода редактором запрещена: плеер формируется по разрешённому провайдеру и идентификатору ролика.

### 6.2. Отзывы о продукции

Сотрудник создаёт и публикует отзывы в Django Admin. Поля: имя автора, организация при наличии, текст, дата, фотография/логотип при наличии, связанный товар или товары, направление, порядок, статус публикации и признак показа на лендинге. Звёздный рейтинг не является обязательным до отдельного согласования.

На лендинг добавляется самостоятельный блок отзывов, оформленный в существующем стиле. На странице товара показываются опубликованные отзывы, связанные с этим товаром. При отсутствии отзывов не выводить вымышленные записи и декоративные рейтинги; для лендинга блок скрывается, для товара допускается нейтральное сообщение.

Точное место блока на лендинге требует уточнения: формулировка «блок с отзывами на товарами» трактуется в этом ТЗ как отзывы о товарах и не фиксирует размещение над или под продуктовой секцией.

Публикация посетителями, загрузка ими файлов, пользовательские оценки и отметка «Подтверждённая покупка» не входят в первую версию без отдельного задания. Заказчик предоставляет подлинные материалы и основания для их публикации.

### 6.3. Обновление контента

Публикация выполняется без пересборки React/Tailwind и перезапуска приложения. Обновлённые данные доступны при следующем открытии страницы или запросе её контента; автоматическое изменение уже открытой страницы в реальном времени не требуется. Если используется кеширование, после изменения сбрасываются кеши затронутых HTML-оболочек, JSON-ответов и страниц магазина. Возврат к странице через клиентскую историю должен перепроверять актуальность данных; кеш React не может бессрочно удерживать старую публикацию. Архивирование товара или документа не удаляет исторические сведения из заказов и журналов.

Публикация новой структуры сцены или изменение кода компонента требует обычного выпуска сборки. Обещание редактирования без пересборки относится к согласованным полям контента, а не к произвольному изменению вёрстки. После загрузки изображений, шрифтов и динамического контента геометрия анимаций пересчитывается без сброса текущей прокрутки.

## 7. Каталог и страница товара

### 7.1. Категории и товары

- Категории управляются через админку: название, slug, описание, изображение при необходимости, порядок и активность.
- Товар содержит название, уникальный артикул, slug, категорию или категории, краткое и полное описание, изображения, цену в рублях, состояние публикации и доступность для покупки.
- Дополнительно поддерживаются характеристики, связанные документы и отзывы. Структура характеристик должна позволять описать масла, гидролаты и оборудование без копирования моделей для каждой категории.
- Цены и суммы хранятся как десятичные значения, без `float`. Количество единиц товара — положительное целое для базового сценария.
- Конкретная продаваемая позиция должна однозначно определяться артикулом. Варианты объёма, комплектации и упаковки согласуются до реализации модели вариантов.
- Скрытые и архивные товары недоступны для новых покупок. Наличие отдельного режима «Под заказ» или «Запросить расчёт» определяется в разделе 17.

### 7.2. Каталог

Каталог показывает фото, название, цену, доступность и переход к товару. Обязательна фильтрация по категориям. Состояние фильтра и страницы списка отражается в URL и восстанавливается при обновлении страницы, передаче ссылки и навигации назад.

Предусмотреть пагинацию и серверное ограничение размера выдачи. Сортировка по цене/названию и поиск по каталогу — дополнительные функции, не входящие в обязательный объём до согласования.

Состояния интерфейса: обычная выдача, пустая категория, отсутствие подходящих товаров, загрузка, ошибка с повтором запроса. Все цены и доступность определяет сервер.

### 7.3. Детальная страница

Страница содержит галерею изображений, описание, характеристики, цену, выбор количества, доступность, кнопку добавления в корзину, связанные PDF и отзывы. Опции товара отображаются, если утверждена модель вариантов.

Недоступный товар нельзя добавить в корзину через интерфейс или прямой запрос. Если между открытием страницы и добавлением изменились цена или наличие, покупатель получает актуальные сведения.

## 8. Корзина в модальном окне

- Корзина открывается из шапки магазина; после добавления товара показывает подтверждение и позволяет перейти к её содержимому.
- В модальном окне отображаются товар, изображение, выбранный вариант при наличии, цена, количество, сумма строки, удаление позиции, общая сумма и переход к оформлению.
- Добавление, изменение количества и удаление выполняются через HTMX без полной перезагрузки. Счётчик корзины и итоговые суммы обновляются согласованно.
- Содержимое хранится на сервере с привязкой к гостевой сессии. Перезагрузка страницы и закрытие модального окна не очищают корзину; время жизни задаётся конфигурацией.
- При нескольких вкладках и пересекающихся запросах сервер сохраняет корректное количество и возвращает актуальную корзину. Запоздалый ответ не должен визуально возвращать старое состояние.
- Пустая корзина имеет понятное сообщение и переход в каталог. Оформление пустой корзины запрещено.
- Неактивные позиции, недопустимые количества и изменения цен проверяются повторно перед заказом.

Модальное окно поддерживает клавиатуру, закрытие по Escape, удержание фокуса внутри, возврат фокуса к вызвавшей кнопке и блокировку прокрутки фона. По [DESIGN-SHOP.md](DESIGN-SHOP.md), раздел 9, корзина выезжает справа на desktop и занимает весь экран телефона; сумма товаров и кнопка оформления расположены над списком позиций. Корзиной управляют HTMX и Alpine.js на домене магазина; React-лендинг ведёт в магазин обычной ссылкой.

Для прямого URL и режима без JavaScript `/cart/` отображает обычную страницу с теми же операциями. Это резервное представление, а не отдельная корзина с собственной логикой.

## 9. Создание и обработка заказа

### 9.1. Оформление

Базовый сценарий — гостевая покупка. Форма содержит имя получателя, телефон, email, согласованный способ получения, необходимые для него адресные поля и необязательный комментарий. Не собирать данные, которые не нужны для выполнения заказа.

Перед подтверждением показываются позиции, количество, стоимость товаров, доставки, итог и условия покупки. Правила получения, расчёта доставки и обязательность контактных полей утверждаются до запуска. Не использовать фиктивную бесплатную доставку как неявное значение по умолчанию.

При отправке сервер заново проверяет товары, цены, наличие, количество, доставку и итог. Изменение цены или состава требует уведомления покупателя и повторного подтверждения до оплаты. Значения сумм из браузера не являются достоверными.

Создание заказа идемпотентно: повторный клик или повтор запроса с тем же ключом оформления не создаёт второй заказ. Уникальность операции обеспечивается на уровне базы данных, а не только отключением кнопки.

В заказ сохраняются неизменяемые снимки наименований, артикулов, выбранных вариантов, цен, количества, налоговых параметров при необходимости, стоимости доставки и контактных данных на момент оформления. Последующее изменение каталога не меняет уже созданный заказ.

### 9.2. Статусы и наличие

Статус исполнения заказа и финансовый статус хранятся отдельно. Предлагаемые статусы исполнения: «Новый», «В обработке», «Передан в доставку / готов к выдаче», «Завершён», «Отменён». Финансовое состояние выводится из подтверждённых платежей и возвратов: «Не оплачен», «Ожидает подтверждения», «Оплачен», «Частично возвращён», «Возвращён».

Правила переходов задаются явно. Менеджер не может произвольно поставить «Оплачен» вместо проверки через платёжный сервис. Отмена оплаченного заказа и возврат денег — связанные, но разные операции.

Рекомендуемая политика для ограниченных остатков: резервирование при создании заказа, подтверждение списания после оплаты, освобождение резерва после подтверждённой отмены или истечения срока. Проверка и резерв выполняются атомарно; параллельные покупки не приводят к отрицательному остатку. Срок резерва и продажа под заказ требуют согласования.

Перед освобождением резерва по таймеру необходимо разрешить неопределённое состояние платежа. Поздний успешный платёж не теряется: если товар уже нельзя выделить, создаётся явно видимая менеджеру ситуация для выполнения заказа либо возврата, без фиктивного подтверждения наличия.

### 9.3. Работа менеджера

В админке доступны поиск по номеру, фильтрация по датам и статусам, просмотр состава, контактов, сумм, способа получения, истории изменений и связанных платежей. Удаление заказов с финансовой историей обычным действием администратора запрещено.

Предусмотреть уведомление магазина о новом заказе и подтверждение покупателю. Рекомендуемый канал первой версии — email; параметры отправителя и получателей согласуются. Ошибка отправки письма не отменяет заказ или платёж; неотправленное уведомление можно повторить без дублирования бизнес-операции.

## 10. Интеграция ЮKassa

### 10.1. Основной сценарий

1. Сервер создаёт заказ и отдельную запись платёжной попытки.
2. Адаптер ЮKassa формирует платёж по серверным данным заказа и сохраняет его идентификатор, ключ идемпотентности и состояние.
3. Покупатель переходит на платёжную страницу ЮKassa.
4. После оплаты покупатель возвращается на страницу заказа; сервер независимо получает и проверяет актуальный статус платежа.
5. При подтверждённом успехе заказ отмечается оплаченным, выполняются необходимые изменения резервов и формируются уведомления.

Основной способ первой версии — банковские карты с поддержкой «Мир». Другие способы, например СБП, включаются после согласования. ЮKassa документирует поддержку карт «Мир» и перехода на свою платёжную страницу: [способы оплаты](https://yookassa.ru/developers/payment-acceptance/getting-started/payment-methods).

### 10.2. Надёжность и проверка платежей

- Секретные ключи используются только на сервере и разделяются для тестовой и рабочей среды.
- Данные банковской карты вводятся на стороне ЮKassa; приложение не принимает и не хранит номер карты, CVC/CVV или одноразовые коды подтверждения.
- Возврат браузера по `return_url` не является доказательством оплаты.
- Входящее уведомление проверяется по актуальным требованиям ЮKassa; перед финансовым переходом сервер получает состояние платежа через авторизованный API и сверяет идентификатор, принадлежность магазину и заказу, сумму, валюту и статус.
- Повторные, запоздавшие и пришедшие не по порядку уведомления не приводят к повторному списанию остатков, повторным уведомлениям покупателю или откату подтверждённого состояния.
- Заказ может иметь несколько платёжных попыток, но нельзя бесконтрольно создавать новые попытки, пока предыдущая находится в неопределённом или активном состоянии.
- При таймауте создания платежа сохраняется состояние для сверки. Повтор той же операции использует тот же ключ идемпотентности; истечение срока гарантии провайдера не означает разрешение создать потенциально второй платёж без проверки.
- Повторное успешное списание по другому идентификатору для уже оплаченного заказа отмечается как финансовая аномалия и передаётся на обработку менеджеру.
- Webhook подтверждается успешным HTTP-ответом только после надёжного сохранения результата или задания на его обработку. При временной ошибке обработка должна быть повторяема.
- Предусмотреть периодическую сверку незавершённых платежей на случай потери уведомления. Реализация — плановое задание либо фоновый обработчик с устойчивым хранением состояния.

Технический протокол сверяется с [документацией уведомлений ЮKassa](https://yookassa.ru/developers/using-api/webhooks) и [правилами идемпотентности](https://yookassa.ru/developers/using-api/interaction-format); собственная защита от дублей хранится в базе приложения.

### 10.3. Возвраты и чеки

До запуска определить порядок возвратов: через кабинет ЮKassa либо действие в Django Admin. В обоих случаях подтверждённые возвраты должны отражаться в финансовой истории приложения; возврат товара на склад является отдельным решением.

Схему фискализации, налоговые параметры, состав и момент выдачи чеков согласовать с заказчиком и его бухгалтером. Реальные платежи не запускаются без определения применимой схемы и её проверки. ЮKassa предоставляет варианты подключения чеков: [документация](https://yookassa.ru/developers/payment-acceptance/receipts/54fz/basics).

## 11. Поведение публичного интерфейса: React и HTMX

### 11.1. Границы работы без перезагрузки

На основном домене лендинг и страницы материалов используют React: существующие интерактивность, анимации и переходы сохраняются, маршрутизатор адаптируется к обычным путям `/materials/` и `/materials/<slug>/`. Переходы между этими React-страницами и фильтрация материалов выполняются без полной перезагрузки; якоря лендинга сохраняют существующее поведение.

В магазине переходы, фильтрация, пагинация, операции корзины и отправка формы заказа выполняются через HTMX с частичным обновлением HTML. Alpine.js отвечает за локальное состояние его интерфейса. React не нужен для реализации магазина.

Переход между `dari-sinergii.ru` и `shop.dari-sinergii.ru`, переход в ЮKassa, скачивание PDF и открытие внешних ресурсов выполняются обычной навигацией. Это явная граница требования: два поддомена являются разными origin, и объединять их в одну браузерную SPA в первой версии не требуется.

Django Admin использует стандартную навигацию Django. Требование HTMX относится к магазину и возможным новым публичным страницам на Django-шаблонах, но не к оболочкам React. Переход между React-страницей и отдельной страницей на Django-шаблоне выполняется обычной навигацией даже на одном домене. Объединение админки и обеих публичных частей в одну SPA не требуется.

### 11.2. Требования к магазину на HTMX / Alpine.js

- Каждая страница магазина имеет обычный URL и доступна при прямом открытии и обновлении.
- Переходы корректно обновляют адрес, заголовок документа, активные элементы навигации и фокус. Назад/вперёд восстанавливают содержимое и состояние списка.
- Различать ответ полной страницы и HTML-фрагмента; при восстановлении истории без кеша отдавать требуемый полный документ. Кеши не смешивают варианты ответа и данные разных пользователей.
- Alpine.js управляет локальным UI, но не рассчитывает авторитетную стоимость заказа и не подтверждает оплату.
- После HTMX-замены новые компоненты корректно инициализируются, старые освобождают обработчики, таймеры и анимации. Повторный переход не создаёт дублирующиеся события.
- Обновление корзины или фильтра не перезапускает несвязанные видео и не сбрасывает необходимое состояние страницы.
- При сетевой ошибке сохраняются введённые данные, отображается понятное сообщение и безопасная возможность повторить действие.
- Формы имеют серверную валидацию с ошибками у полей. Отправка HTMX поддерживает ответы валидации; нельзя молча оставлять ошибку только в консоли.
- Нельзя сохранять страницы с персональными данными, корзиной или платежом в небезопасный общий либо браузерный кеш истории HTMX. Возврат назад не должен показывать устаревший финансовый статус.
- При отключённом JavaScript ссылки магазина, каталог, полная страница корзины и оформление остаются доступны через обычные формы и навигацию. Требования к основному React-сайту в этом режиме определены в разделе 11.4.

Использовать штатные механизмы HTMX с учётом [навигации `hx-boost`](https://htmx.org/attributes/hx-boost/) и [контроля истории](https://htmx.org/reference/); точная конфигурация фиксируется для выбранной версии.

### 11.3. Сохранение поведения React-сайта

- Существующие JSX-компоненты, стили и анимационные сценарии являются основой переноса. Изменение источника данных не должно заменять их новой визуально приблизительной реализацией.
- При прямом запросе известного маршрута Django выдаёт нужную оболочку и данные. Для неизвестной или неопубликованной подборки возвращается HTTP 404; Nginx не подменяет все неизвестные пути ответом `200` с лендингом.
- React-маршрутизация обновляет URL, заголовок документа, фокус и состояние страницы. Назад / вперёд восстанавливают подборку, фильтр и положение прокрутки, включая возврат к отраслевому слайду. Неудачная загрузка нового маршрута даёт согласованные URL и сообщение об ошибке.
- После монтирования и изменения размеров содержимого синхронизируются GSAP/ScrollTrigger/Lenis. При размонтировании удаляются обработчики, таймеры и анимационные контексты. Повторные переходы и React StrictMode не создают двойные анимации.
- Состояние мобильного меню и прокрутки принадлежит React; HTMX и Alpine.js не заменяют HTML внутри его корня. Начальные данные монтируются через React, а не имитируют hydration отсутствующей серверной React-разметки.
- Сохраняются `prefers-reduced-motion`, резервное отображение видео, поведение якорей и исправления Safari/iPhone. Новые отзывы, видео и документы имеют состояния загрузки, отсутствия данных и ошибки, вписанные в исходный дизайн.
- Возврат посетителя из магазина не очищает серверную корзину; React-лендинг не хранит её независимую копию и не рассчитывает суммы.

### 11.4. Начальный HTML, SEO и режим без JavaScript

Django выдаёт для каждого публичного маршрута корректные `title`, description, canonical и Open Graph до выполнения JavaScript. Они формируются из того же опубликованного контента, что и данные страницы. При клиентском переходе React обновляет соответствующие метаданные. Наличие JSON в HTML не означает, что весь видимый текст React доступен поисковику без выполнения JavaScript.

При отключённом JavaScript основной сайт показывает серверное резервное содержимое: название и краткое описание компании, контакты, ссылку в магазин, а на страницах материалов — название подборки и прямые ссылки на опубликованные PDF. Полное воспроизведение анимаций и React-интерфейса без JavaScript не требуется. При сбое загрузки JS или ошибке React предусмотрен доступный аварийный блок с повтором, контактами и ссылкой в магазин; один `noscript` такой сбой не покрывает.

Если потребуется полное серверное представление всего содержимого лендинга для SEO, SSR / prerender проектируется отдельно с учётом публикации CMS без пересборки. В базовой версии не обещается SSR только на основании использования Django. Магазин остаётся серверно отрисованным и сохраняет обычные формы без JavaScript.

## 13. Требования к качеству кода

- Использовать ООП там, где она выражает ответственность и инварианты: предметные операции, сервисы и адаптер платёжного провайдера. Простые функции допустимы; классы не создаются исключительно ради формального соответствия ООП.
- Соблюдать DRY для бизнес-правил: расчёт корзины, проверка цены, переходы статусов и обработка платежей имеют единый источник логики для обычных форм, HTMX и административных действий.
- Views и формы отвечают за HTTP, валидацию и вызов операций. Шаблоны не содержат финансовой бизнес-логики. Модели и отдельные сервисы разделяются по обоснованной ответственности.
- Django ORM используется для работы с данными. Дополнительный универсальный repository-слой поверх ORM не обязателен без реальной потребности.
- На границах интеграций применять явный маппинг: DTO / типизированные структуры для создания платежа, разбора ответа и сопоставления внешних статусов внутренним. Для React определить контракт публичного контента и адаптер из серверных данных в props компонентов; не выдавать модель целиком и не передавать бесконтрольно словари провайдера во все слои приложения.
- React-компоненты могут оставаться функциональными с hooks; требование ООП не обязывает переводить существующий интерфейс в классовые компоненты. Загрузка и нормализация контента отделяются от анимационных эффектов и представления; перенос всего исходного JSX на TypeScript не является обязательным условием миграции.
- Не дублировать один источник данных одновременно в модели, JS-состоянии и HTML без правил синхронизации. Источник истины для заказа и оплаты — сервер.
- Применять транзакции и блокировки для конкурентных операций. Не удерживать длительную транзакцию PostgreSQL во время запроса к внешнему платёжному API.
- Избегать скрытой оркестрации платежей через цепочки Django signals. Денежные операции должны иметь явную точку входа и предсказуемый порядок выполнения.
- Использовать типизацию в сервисах и интеграциях, форматирование, линтеры, миграции и фиксированные зависимости. Исключения обрабатываются по типу и контексту, ошибки не подавляются без записи и восстановления.
- Следить за N+1-запросами, использовать пагинацию, необходимые индексы, `select_related` / `prefetch_related` по результатам анализа запросов.
- Документировать нетривиальные решения, переходы состояний и правила восстановления. Не создавать абстракции и инфраструктуру для гипотетических будущих функций.

## 14. Безопасность и защита данных

### 14.1. Приложение и доступ

- HTTPS на основном домене, магазине и админке; доверенный сертификат с настроенным продлением. Перенаправление HTTP включается после проверки HTTPS; HSTS — после проверки всех затронутых доменов.
- Production запускается с `DEBUG=False`, ограниченными `ALLOWED_HOSTS`, проверенными CSRF-origin и корректными настройками доверенного reverse proxy.
- Session cookies защищены `Secure`, `HttpOnly` и подходящим `SameSite`. Политика проверяется вместе с возвратом из ЮKassa.
- CSRF-защита обязательна для пользовательских операций изменения, включая HTMX. GET-запросы не изменяют заказ и корзину. Исключение для webhook ограничено конкретным маршрутом и компенсируется проверкой отправленного события.
- Секреты передаются через окружение или систему секретов; отсутствуют в Git, клиентском коде, образах общего доступа и журналах. Любые значения, попавшие в Vite-сборку, включая `VITE_*`, считаются публичными; ключи Django, БД и ЮKassa туда не передаются.
- Права доступа и принадлежность заказа/корзины проверяются независимо от типа запроса и наличия заголовка HTMX. Правила публикации одинаковы для HTML, начального JSON, публичного JSON-интерфейса и выдачи файлов; скрытие компонента в React не является защитой черновика.
- Ограничиваются частота попыток входа, создания заказов, запуска оплаты и других чувствительных операций. Защита не мешает повторам уведомлений провайдера.

Настройки сверяются с [deployment checklist Django](https://docs.djangoproject.com/en/stable/howto/deployment/checklist/); в CI и при выпуске выполняется `manage.py check --deploy` с production-параметрами.

### 14.2. Контент, загрузки и браузер

- Экранировать вывод, очищать форматированный контент по разрешённым тегам, проверять URL. Не применять `safe` или React `dangerouslySetInnerHTML` к непроверенному содержимому. Начальный JSON передавать безопасным сериализатором; разрешённые схемы ссылок и источники видео проверять на сервере.
- Проверять расширение, фактический тип, размер и назначение загружаемого файла. Лимиты задавать согласованно в Django и Nginx.
- Загруженные файлы не исполняются как код и не могут перезаписать шаблоны или статические ресурсы. Пути формируются сервером; traversal исключён.
- Локальные имена медиа — латиница/UUID. Заголовки типа содержимого и скачивания формируются безопасно; PDF открываются и скачиваются по рабочим адресам.
- Проектировать CSP отдельно для React-страниц с GSAP/Lenis и магазина с HTMX/Alpine.js, учитывая видео, динамические стили анимаций и платёжный переход. Проверять её на production-сборках; разрешения для Vite HMR из разработки не переносятся в production. Предпочтительна CSP-совместимая сборка Alpine; не отключать политику ради обхода проблемы. [Описание Alpine CSP build](https://www.alpinejs.dev/advanced/csp).
- Защитить интерфейс от clickjacking, выдавать `nosniff`, определить Referrer Policy. CORS не открывается для всех источников с учётными данными.

### 14.3. Персональные данные

Собирать минимальные данные заказа, ограничить их видимость по ролям, не включать их в адреса страниц и технические логи. Определить сроки хранения, удаление/обезличивание, местоположение инфраструктуры и необходимые документы вместе с заказчиком. Не публиковать резервные копии или выгрузки через web-каталог.

До запуска заказчик предоставляет актуальные реквизиты, условия продажи и доставки, политику обработки данных и необходимые формулировки согласий. Их содержание не подменяется случайным шаблоном исполнителя.

## 15. Развёртывание и эксплуатация

- Предусмотреть локальную, тестовую и production-среды. Рабочие ключи и персональные данные не переносятся в тестовую среду без отдельной процедуры.
- Docker Compose описывает приложение, PostgreSQL и Nginx. Для плановых задач нужен отдельный процесс/сервис либо планировщик; Redis/Celery не являются обязательными, если надёжность обеспечена более простым способом.
- Для Django использовать production WSGI/ASGI-сервер, например Gunicorn; `runserver` в production запрещён.
- React/Vite и Tailwind магазина собираются отдельно на стадии сборки из фиксированных зависимостей. Node.js нужен для инструментов разработки и сборки; постоянно работающий Node.js-сервис в базовом production не требуется. Production не зависит от Vite dev-сервера или Tailwind CDN.
- Nginx направляет динамические страницы и JSON-запросы в Django, раздаёт версионированные ресурсы React и магазина. Django подключает файлы по manifest текущего релиза; сохраняется согласованность шаблонов, контракта данных и сборки при выпуске и откате. Хешированные JS/CSS кешируются длительно, публичный контент — с управляемой актуализацией, персональные данные — без общего кеша.
- Настроить healthcheck, перезапуск процессов, ограниченные права контейнеров, закрытый доступ к базе и разделение публичной статики, публичных медиа и защищённых файлов.
- Миграции выполняются управляемо одной процедурой выпуска. Перед потенциально разрушающим изменением создаётся резервная копия.
- Данные PostgreSQL и загруженные файлы хранятся вне эфемерного слоя контейнера. Пересоздание контейнеров не теряет контент, заказы и файлы.
- Настроить резервное копирование базы и медиа, хранение копий вне публичного каталога и проверку восстановления. Рабочее предложение — ежедневные копии плюс копия перед релизом; допустимая потеря новых заказов и сроки восстановления требуют согласования.
- Журналировать ошибки приложения, платежных интеграций и плановых задач с идентификатором запроса/заказа. Настроить контроль доступности, места на диске, срока сертификата и зависших платежей.
- CI выполняет проверки Python и клиентского кода, тесты, проверку миграций, сборку React/Vite и стилей магазина, проверку подключения manifest и ресурсов. Production-выпуск должен иметь воспроизводимую процедуру и точку возврата.

Существующая загрузка статического ZIP через ispmanager не является способом развёртывания Django. Нужен сервер или услуга хостинга с поддержкой указанного стека и долговременных процессов. Конкретный тариф REG.RU / VPS выбирается отдельно. GitHub хранит код и может запускать CI/CD; GitHub Pages не исполняет Django и PostgreSQL.

Адаптированный React-маршрутизатор переводит их в `/materials/` и `/materials/sport/` с заменой текущей записи истории. Существующий обработчик `hashchange` не должен конкурировать с новым роутером; обычные якоря лендинга и смысл действия «Вернуться к сайту» сохраняются.

Корзина, оформление, заказы, предпросмотр и админка не индексируются; эта настройка не заменяет контроль доступа.
- При откате после запуска магазина нельзя просто восстановить старую базу поверх новых заказов. План возврата версии должен сохранять поступившие заказы, платежи и загруженный контент.

### 16.2. Обязательные проверки

1. Модели и сервисы: ограничения данных, суммы, доступность, статусы, роли, публикация.
2. HTTP-интерфейс: страницы и HTMX-фрагменты магазина, React-оболочки и JSON-контракты, CSRF, ошибки форм, прямые URL и HTTP 404, отсутствие доступа к чужим заказам и черновикам через все каналы выдачи.
3. Корзина: добавление, изменение, удаление, пустое состояние, несколько вкладок, перезагрузка и недоступный товар.
4. Заказы: повторная отправка, изменение цены, конкурентная покупка последней единицы, сохранность снимков после изменения каталога.
5. ЮKassa: успех, отмена, временная ошибка, таймаут, дубли и неверные уведомления, другая сумма/валюта, восстановление после потерянного webhook, поздний платёж и возврат. Автоматизированные тесты не проводят реальные списания.
6. Браузерные сценарии: полный путь от каталога до результата оплаты в тестовой среде; React- и HTMX-навигация в своих границах, переходы между доменами, назад/вперёд, якоря, восстановление истории, ошибки сети; работа магазина без JavaScript и резервное содержимое React-страниц.
7. Визуальное сравнение: контрольные размеры 1440, 768, 390 и 320 CSS-пикселей, основные сцены и новое содержимое. Для лендинга сравнить также записи анимаций, прокрутку, меню и повторный вход на страницу; для магазина применить дополнительные размеры и критерии DESIGN-SHOP.md.
8. Браузеры: актуальные Chrome, Firefox, Edge, Safari и мобильные Chrome/Safari. Проверка Safari включает реальные особенности iPhone; эмуляция ширины сама по себе её не заменяет.
9. Доступность: клавиатура, фокус модальных окон, подписи полей, альтернативные тексты, читаемость ошибок, `prefers-reduced-motion`, отсутствие горизонтального переполнения.
10. Эксплуатация: чистый запуск Docker-окружения, миграции, сохранность данных при перезапуске, HTTPS и пробное восстановление резервной копии.
11. CMS → React: публикация и снятие с публикации текста, отзыва, видео и PDF без пересборки; сброс серверного кеша, актуализация при повторном открытии, ошибка JSON-запроса, отсутствие утечек предпросмотра.
12. Сохранение фронтенда: исходные применимые тесты React/платформы продолжают проходить; manifest, пути ресурсов, старые hash-ссылки, отсутствие влияния Tailwind на лендинг и двойных GSAP/Lenis-обработчиков проверены.

Проверки должны тестировать поведение и бизнес-инварианты. Требование «лучшие практики» не заменяется формальным процентом покрытия тестами.

Численные требования к нагрузке, времени ответа и допустимому простою фиксируются до нагрузочной приёмки на согласованном сервере и объёме каталога. Обязательный минимум — пагинация, отсутствие N+1 в типовых списках, оптимизированные изображения и отсутствие перезагрузки всей страницы при локальных операциях.
