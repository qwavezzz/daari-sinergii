## SEO: фактическое состояние

Главный sitemap содержит 10 информационных URL. Они доступны без авторизации,
имеют canonical, title, description и один H1. В проверенных HTML нет изображений
без атрибута alt. Основной сайт открыт поиску; магазин уже имеет HTML `noindex`.
HTTP и www приводят к HTTPS основного адреса. Несуществующая страница возвращает
настоящий 404, а не 200 с текстом ошибки.

В отрисованном DOM четырёх проверенных типов страниц JSON-LD не обнаружен.
Структурированные данные — следующий этап после уточнения реальных сведений об
организации. Product/Offer для вымышленного ассортимента добавлять не нужно.

Основной пробел содержания — короткие вводные HTML-страницы, подробности преимущественно
в PDF. Нужны согласованные ответы о продукции/услугах, реквизиты, авторство и
доказательные источники. Приоритеты запросов, конкуренты и регион ещё не исследованы.
Короткая description сама по себе не является технической ошибкой; её следует
писать под полезный сниппет, а не добирать до формального числа символов.

Google Search Console и Яндекс Вебмастер, по данным разработчика, не настроены.
[Пошаговая настройка и план контента](SEO-SETUP.md). Использован прочитанный
[чеклист seo-audit](https://github.com/coreyhaines31/marketingskills/blob/main/skills/seo-audit/SKILL.md),
без установки сторонних исполняемых скриптов. Политика запрета индексации сверена с
[Google Search Central](https://developers.google.com/search/docs/crawling-indexing/block-indexing).

Полевые Core Web Vitals, поисковые позиции и органический трафик не измерены.
Браузерная проверка показывает работоспособность выбранных сценариев, а не скорость
у всех посетителей и не полное соответствие требованиям доступности.

## Почта и DNS

| Запись | Ответ публичного резолвера 18.09.2026 |
|---|---|

| Основной домен / shop A | `134.0.113.203` |

| SPF | одна запись, разрешающая `ip4:31.31.197.73 a mx include:_spf.hosting.reg.ru ~all` |
| DMARC | `p=none; aspf=r; sp=none` — режим наблюдения |
| DKIM | dkim._domainkey.dari-sinergii.ru: Google и Cloudflare вернули присланный RSA-ключ 2048 бит. Публикация подтверждена; подпись внешнего письма не проверена |

Необходимость разрешённого SPF IP `31.31.197.73` уточнить по действующей почтовой
услуге; наличие другого A-адреса у VPS не доказывает ошибку. DNS не менялся.
Нужен тест на согласованный ящик с SPF/DKIM/DMARC=pass и проверкой Reply-To.
Текущая инструкция — [EMAIL.md](../deploy/EMAIL.md).

Позднее разработчик выполнил `sendtestemail` с VPS и подтвердил получение письма
на свой личный ящик. Он уточнил, что указал только личный адрес: почта сайта
получателем не была, поэтому отсутствие копии не является признаком сбоя.
Затем разработчик отдельно отправил тест на почту сайта и подтвердил доставку.
Таким образом, оба адреса получили тестовые письма с VPS. Скриншот Roundcube
подтвердил тест во «Входящих» ящика сайта; папка личного ящика отдельно не подтверждалась.
SPF/DKIM/DMARC и Reply-To уведомлений пока не подтверждены. Тестовое письмо
не создаёт заказ и не обрабатывает очередь. Разработчик затем прислал состояние
таймера `active/waiting`, `enabled`, последний запуск 18.09.2026 15:02:40 MSK;
служба завершилась тогда же с `Result=success`, `ExecMainStatus=0`.
Последующая проверка БД после выпуска показала `pending_mail: 0`,
`mail_with_errors: 0`: очередь пуста, текущих записей с ошибкой нет.
Это подтверждено отдельно от кода 0 службы: команда сохраняет ошибки отдельных
отправок в Notification для повтора и может завершиться успешно.
Разработчик использует `webmail.hosting.reg.ru`; инструкция просмотра заголовков
добавлена в EMAIL.md. Результаты SPF/DKIM/DMARC пока не получены.
Разработчик проверил исходник письма и сообщил об отсутствии `Authentication-Results`;
других ящиков, кроме REG.RU, у него нет. Поэтому тесты не подтверждают внешнюю
доставку или прохождение SPF/DKIM/DMARC. Отсутствие заголовка не считается доказанным
сбоем. Присланный затем исходник письма на ящик сайта не содержит и `DKIM-Signature`.
Видимый маршрут проходит от mail1.hosting.reg.ru к sm38.hosting.reg.ru; отправитель
и получатель — один ящик домена. Внешняя подпись этим тестом не проверена.
Повторная проверка NS/MX/SPF/DMARC подтвердила прежние опубликованные значения
(`artifacts/readiness/dns-mail-readiness.json`). Пользователь назвал Roundcube Webmail
1.6.17; панель управления почтовой услугой и настройка DKIM ещё не определены.
Позднее пользователь открыл DNSadmin и подтвердил наличие `dari-sinergii.ru`.
Нужная DNS-зона найдена. Из неё пользователь прислал DKIM TXT `v=DKIM1; k=rsa;
s=email; p=…` и прежнее значение DMARC. OpenSSL успешно прочитал публичный RSA-ключ
2048 бит (DER 294 байта); артефакт — `artifacts/readiness/dkim-key-supplied.json`.
Затем пользователь уточнил имя `dkim._domainkey.dari-sinergii.ru.`. Google и Cloudflare
независимо вернули по одному TXT с тем же ключом; SHA256 DER совпадает.
Артефакт — `artifacts/readiness/dkim-public-dns.json`. Публикация DKIM подтверждена.
`s=email` в TXT — тип сервиса, не селектор. Подписывание внешних писем SMTP-сервером
ещё не подтверждено; опубликованную запись пересоздавать не требуется.
На присланном скриншоте по-прежнему открыт Roundcube. В списке входящих видны также
письма о создании/отмене заказа за предыдущий день; это ограниченное свидетельство
доставки прежних уведомлений, не полная приёмка сценария в новом релизе.
