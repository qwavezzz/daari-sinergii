## Что реализовано

- Суммы, наличие, резервы и подтверждение платежа проверяет сервер.
- CSP разрешает переход только на выбранный REST-шлюз Альфа-Банка на страницах
  оформления и заказа. Обычные формы и HTMX проверяются отдельно.
- Письма о создании и оплате идут покупателю и менеджеру через очередь с повторами.
  **Пробная оплата не отправляет писем.**
- Единственная настройка получателя: **Заказы → Почтовые уведомления → Email
  менеджера**, затем `MANAGER_EMAIL`, если поле пустое. Миграция переносит прежний
  адрес из настроек магазина, сохраняя приоритет существующей почтовой настройки.
- Ссылка из письма открывает только соответствующий заказ с другого устройства.
  Срок по умолчанию 30 дней от отправки; проверяется при каждом открытии. Подмена
  ссылки, смена email или увеличение `Order.access_version` отменяют доступ.
  UUID без исходной сессии или действующей ссылки недостаточно. Ссылка является
  секретом доступа: не пересылайте её посторонним. После открытия токен убирается
  из адресной строки; настройки Nginx/Gunicorn исключают его из access log.
- В оплаченном заказе менеджер может сохранить трек-номер и поставить письма в
  очередь. Повтор того же действия не создаёт повторных уведомлений. Накладная
  по-прежнему оформляется вручную.
- `check_store_readiness` разделяет подачу в банк и реальные продажи;
  `check_store_operations` контролирует задержки и ошибки фоновых операций.

## Два этапа готовности

Команды запускают под **тем же окружением, что и Gunicorn**, после миграций.
На VPS это `/etc/dari/dari.env`; корневой `.env` автоматически не читается.
Локальное окружение разработки намеренно не получает статус готовности production.

```bash
python manage.py check_store_readiness --stage review --strict
python manage.py check_store_readiness --stage live --strict
python manage.py check_store_operations --strict --json
```

`review`: реальные товары, реквизиты, тексты, измеренные упаковки, рабочий расчёт
СДЭК, SMTP и протоколы внешней проверки. **Рабочие ключи банка не требуются.**
Пробную оплату и учебную стоимость доставки нужно выключить. Без банка заказ
сохраняется, покупатель видит статус; деньги не списываются.

`live`: дополнительно включён рабочий REST-эквайринг, получено разрешение банка,
согласованы касса/налоги, записаны результаты банковской и кассовой приёмки.
Ненулевой код `--strict` запрещает считать этап завершённым. Команда ничего не
включает автоматически и не вызывает внешние API.

Владелец записывает фактически проведённые проверки в **Система → Приёмка
магазина**: дата, среда, ответственный и номер/ссылка на протокол. Не записывайте
успех по одному наличию ключей. Протокол действует 90 дней; изменения связанных
настроек/товаров/упаковок отменяют его соответствие. Для оформления и эксплуатации
учитывается имя каталога выпуска: каждый выпуск на VPS размещайте в новом каталоге.
Запись протокола подтверждает заявление ответственного, а не автоматический доступ
приложения к почтовым ящикам, кассе или бухгалтерским документам.

## СДЭК: стоимость без скрытой доплаты продавца

1. Внести реальные товары. Для общей коробки указать вес и размеры товара с
   индивидуальной защитой; для отдельной посылки — вес брутто и внешние размеры.
2. Измерить закрытые посылки, заполнить коробки и воспроизводимые инструкции.
   В админке подтвердить замеры после физической сборки. Учебные схемы не подходят.
3. Для каждого артикула обеспечить подтверждённую отдельную посылку или схему
   одной единицы. Это резервный вариант для разных количеств и смешанных корзин.
   Добавить более выгодные подтверждённые схемы типовых заказов.
4. Включить рабочий договор: `CDEK_TEST_MODE=false`, `CDEK_DEMO_QUOTES_ENABLED=false`,
   `CDEK_ENABLED=true`; указать клиентские ключи. Отправитель: согласованные
   `CDEK_FROM_CITY_CODE=431`, `CDEK_FROM_PVZ_CODE=TLT3`; подтвердить их в договоре.
5. Для каждого тестового заказа сравнить сайт и накладную: договор, пункт отправки,
   тариф, город/ПВЗ получателя, каждое место, вес брутто, внешние размеры, объявленную
   стоимость и страховку. Сайт берёт `total_sum`, включая услуги калькулятора.
6. Проверить разные регионы, тяжёлую и смешанную корзину, несколько мест,
   ограничения ПВЗ, недоступный API и изменение корзины после расчёта.
7. Первые реальные счета перевозчика сверить с оплаченными суммами доставки.

При сборке использовать сохранённую в заказе схему. Замена коробки после оплаты
требует пересчёта и решения менеджера до отправки. Своя тара, труд упаковщика,
договорные доплаты и остатки коробок автоматически не тарифицируются: включить
их в экономику товара. Наложенный платёж и повторную оплату доставки не включать.
Подробности: [PACKING-AND-CDEK.md](PACKING-AND-CDEK.md).

## Альфа-Банк и касса

04.10.2026 владелец подтвердил, что тестовые банковские доступы ещё не выданы.
Готовый запрос: [ALFABANK-TEST-ACCESS-REQUEST.txt](ALFABANK-TEST-ACCESS-REQUEST.txt).
Он не отправлялся автоматически. Проверку создания неоплаченного заказа и
писем о создании можно провести без банка, после устранения препятствий доставки
или на изолированном стенде. Успешная оплата, отказ, повтор, возврат и связанные
с ними письма остаются отдельной приёмкой с банковскими реквизитами.

Адаптер реализует `register.do` / `getOrderStatusExtended.do` шлюза
`alfa.rbsuat.com` (тест) / `pay.alfabank.ru` (рабочий). Ответ статуса должен
включать проверяемые суммы оплаты/возврата и merchant-параметры заказа.
Реквизиты другого API, включая i-логины, нельзя просто подставить в эти поля.
Согласовать магазин **shop.dari-sinergii.ru**, возврат на страницу заказа и
callback `https://shop.dari-sinergii.ru/payments/alfabank/webhook/`.

На отдельном стенде с тестовыми реквизитами проверить оплату, отказ, повтор,
потерянный callback, поздний ответ и возвраты. SMTP должен работать и в этом
контуре. На публичном магазине не выставлять тестовый шлюз для обычных покупателей.
После разрешения банка переключить окружение и выполнить контрольную покупку.
Оплата по возврату браузера не подтверждается: нужен результат API банка.

**Кассовая интеграция зависит от выбранного сервиса и требует отдельной приёмки.**
`ALFABANK_RECEIPT_MODE=bank` передаёт корзину банку, но не доказывает выдачу чека.
`external` не подключает внешнюю кассу. В приложении нет универсального адаптера
внешней кассы, автоматического учёта её ошибок и самостоятельного зачёта предоплаты.
До выбора сервиса нельзя честно считать эту часть законченной.

С бухгалтером и кассовым сервисом согласовать НДС/СНО, признак расчёта, маркировку
ассортимента и чеки при оплате, передаче товара, частичном/полном возврате. Проверить
фактические чеки и контроль ошибок у провайдера; записать протокол `fiscal` только
после проверки всей согласованной схемы. Уведомления магазина не являются чеками.

Публичные источники: [требования и подключение Альфа-Банка](https://alfabank.ru/sme/payservice/internet-acquiring/docs/process/),
[основной шлюз](https://alfabank.ru/sme/payservice/internet-acquiring/docs/documentation/),
[i-логины](https://alfabank.ru/sme/payservice/internet-acquiring/docs/documentation-i/),
[ФНС о чеках интернет-магазина](https://www.nalog.gov.ru/rn50/news/activities_fts/16201227/).
Причина прежнего отказа неизвестна; эти проверки не являются гарантией одобрения.

## Приёмка писем

Для текущего этапа без банковских доступов подготовлена отдельная
[проверка неоплаченного заказа на VPS](UNPAID-ORDER-CHECK.md): штатное оформление,
резерв, очередь создания, ссылка и отмена. Публичные способы доставки и env
не меняются. По просьбе владельца рабочий СДЭК и реальные товары пока отложены.
04.10.2026 пользователь предоставил результат VPS: проверочный заказ на 1290 руб.
не оплачен, одна единица DEMO-001 зарезервирована, повтор запуска использовал
существующий заказ. Оба письма о создании приняты SMTP с первой попытки, без ошибок.
Покупатель подтвердил получение письма о создании, отмену заказа и получение
письма об отмене. Вывод состояния после отмены пока не предоставлен: освобождение
резерва и состояние очереди отмены ещё не подтверждены. Корпоративный ящик пока недоступен для проверки;
получение компанией и открытие ссылки в инкогнито также ожидают подтверждения.
Протокол — issue 08 в локальном трекере.

Дополнительно на опубликованном магазине проверены ответы 404 для заказа без
доступа, 410 для неверного email-токена, 403 для оформления без CSRF, запрет
кеширования закрытых страниц, перенаправление HTTP → HTTPS и ответ `/health/` 200.
Запросов к СДЭК или банку при этой проверке не было. Полный CI операторского
скрипта на GitHub завершился успешно. Это не заменяет положительную проверку
ссылки из полученного письма и итоговых остатков на VPS.

1. Указать согласованный корпоративный `info` в «Почтовых уведомлениях»; проверить
   адрес на рабочем столе админки. Старое заполненное поле имеет приоритет над env.
2. Настроить `EMAIL_HOST`, порт, TLS/SSL, пользователя/пароль, `DEFAULT_FROM_EMAIL`.
   `send_notifications --check` проверяет настройки без отправки.
3. `check_integrations --only email` проверяет SMTP-соединение;
   `--send-test-email` **отправляет** проверочное письмо текущему менеджеру.
4. Создать заказ через тестовый банковский контур и оплатить его. Получить письма
   о создании и оплате на адрес покупателя и компании. Открыть ссылку в другом браузере.
5. Проверить входящие/спам, SPF/DKIM/DMARC по заголовкам внешнего получателя;
   воспроизвести сбой SMTP на стенде и дождаться повторной отправки.

## Критерии выпуска

| Сценарий | Ожидаемый результат |
| --- | --- |
| Двойное нажатие | Один заказ и одна активная попытка оплаты |
| Последняя единица одновременно у двух покупателей | Только один действующий резерв; проверка на PostgreSQL |
| Изменённая корзина/упаковка/ПВЗ | Старый расчёт отвергнут, новый подтверждён покупателем |
| Ошибка СДЭК | Нет бесплатной доставки и заказа с неподтверждённой ценой |
| Форма с JS и без JS | Переход в банк и безопасный повтор |
| Потерянный callback | Оплата найдена фоновым запросом к банку |
| Письмо на другом устройстве | Доступ только к своему заказу; чужая/истёкшая ссылка отклоняется |
| Сбой SMTP | Заказ сохранён, письмо остаётся в очереди и повторяется |
| Возврат | Суммы банка, заказа и чеков согласованы |
| Упаковка и накладная | Выбранные места совпадают с физической сборкой и счётом |

Порядок установки, таймеры, резервные копии и восстановление — в
[deploy/README.md](../deploy/README.md). Результаты локальных тестов не заменяют
проверку конкретного рабочего VPS, договора, SMTP и кассы.
