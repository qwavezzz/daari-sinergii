# Проверка неоплаченного заказа без СДЭК

Операторская проверка для текущего установленного магазина, пока банковских
доступов нет. Владелец согласовал её 04.10.2026; рабочий СДЭК и реальный ассортимент
отложены. Используется `deploy/check_unpaid_order.py`.

Скрипт вызывает штатные страницы корзины и обработчик оформления внутри процесса
Django на VPS с проверкой CSRF. Он создаёт один неоплаченный заказ с пометкой
«ТЕСТ» и комментарием «не собирать и не отправлять», резервирует одну единицу
доступного DEMO-товара и ставит два обычных уведомления о создании в очередь.
Их отправляет существующий минутный таймер. Контрольный email покупателя должен
принадлежать оператору и отличаться от текущего адреса менеджера.

Для этой проверки внутри одной транзакции создаётся способ получения
«Проверка неоплаченного заказа — без отправки» с ценой 0. Он удаляется до commit;
другие соединения PostgreSQL не видят его. Название и нулевая цена сохраняются
только в проверочном заказе. Настройки процесса временно отключают пробную оплату
и СДЭК; env и настройки запущенного веб-приложения не меняются. Банк обязан быть
выключен, банковская среда — тестовой. Накладные, платежи и чеки не создаются.

Перед сохранением проверяются серверная цена (несмотря на подставленную клиентом),
отказ без CSRF, повторный POST без второго заказа или резерва, две записи очереди,
доступ владельца, отказ по одному UUID, отказ по испорченной ссылке и доступ из
новой сессии по настоящей подписанной ссылке из текста письма. Любая ошибка этих
проверок откатывает транзакцию целиком. Полные ссылки с токенами не выводятся.

Это приёмка серверного обработчика, базы и очереди на VPS. Сетевой путь через
Nginx/HTTPS проверяется вручную открытием полученного письма. Скрипт не подтверждает
публичное оформление в браузере с действующим СДЭК или банковскую оплату.

## Запуск

Получить скрипт из проверенного коммита GitHub, сверить SHA256 и установить как
`/srv/dari/shared/unpaid-acceptance/check_unpaid_order.py` с владельцем `root:dari`
и правами 0640; каталог — 0750. Не запускать непроверенный файл от root.

Из root-терминала VPS выполнять действия через изолированный transient unit:

```bash
bash <<'BASH'
set -euo pipefail
test "$(id -u)" -eq 0
release=$(readlink -e /srv/dari/current)
case "$release" in /srv/dari/releases/*) ;; *) exit 1 ;; esac
exec 9>/run/lock/dari-release.lock
flock -n 9
read -r -p 'Your customer email (different from manager): ' buyer </dev/tty
systemd-run --quiet --wait --pipe --collect \
  --uid=dari --gid=www-data -p SupplementaryGroups=dari \
  --working-directory="$release" -p EnvironmentFile=/etc/dari/dari.env \
  --setenv="DARI_QA_BUYER_EMAIL=$buyer" \
  "$release/.venv/bin/python" \
  /srv/dari/shared/unpaid-acceptance/check_unpaid_order.py create
BASH
```

Маркер `UNPAID_ORDER_CHECK_OK` и `created_now: true` подтверждают выполнение
проверок и сохранение заказа. Повтор `create` с тем же run ID и email возвращает
тот же заказ; если он уже отменён, новый не создаётся. По умолчанию run ID —
`unpaid-20261004`. Для новой согласованной проверки задаётся другой `--run-id`.

Дождаться писем о создании на адрес покупателя и менеджера. Открыть клиентскую
ссылку в другом браузере / инкогнито: заказ доступен, сумма и состав правильные,
оплата не подтверждена. Менеджерская ссылка ведёт в админку с авторизацией.
Не отправлять токены, полные ссылки или персональные данные в отчёт.

Затем получить фактическое состояние очереди и отменить только этот заказ:

```bash
bash <<'BASH'
set -euo pipefail
test "$(id -u)" -eq 0
release=$(readlink -e /srv/dari/current)
case "$release" in /srv/dari/releases/*) ;; *) exit 1 ;; esac
exec 9>/run/lock/dari-release.lock
flock -n 9
for action in status cancel; do
  systemd-run --quiet --wait --pipe --collect \
    --uid=dari --gid=www-data -p SupplementaryGroups=dari \
    --working-directory="$release" -p EnvironmentFile=/etc/dari/dari.env \
    "$release/.venv/bin/python" \
    /srv/dari/shared/unpaid-acceptance/check_unpaid_order.py "$action"
done
BASH
```

После отмены ожидаются `status: canceled`, `payment: unpaid`, резерв `released`,
две новые записи очереди отмены и возврат зарезервированной единицы в доступный
остаток. Сам заказ сохраняется для протокола. Существующий reconcile также может
отменить его по окончании стандартного резерва (по умолчанию 30 минут).
При следующей проверке `status` у обоих уведомлений создания должны быть `sent_at`
и пустой `last_error`. `sent_at` означает принятие SMTP; получение подтверждается
отдельно в обоих ящиках. После отмены аналогично проверить письма отмены.

Сбой SMTP и повтор проверяются в автоматических тестах с подменой почтового
транспорта. Рабочий SMTP намеренно не отключается. Протоколы приёмки в админке
скрипт не заполняет: сначала нужны фактические результаты оператора.
