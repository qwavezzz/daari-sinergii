# Уведомления о заказах

Актуально на 18 сентября 2026: SMTP настроен через REG.RU. Разработчик выполнил
`sendtestemail` на VPS и подтвердил получение письма на свой личный ящик, затем
отдельным запуском — на почту сайта. Доставка тестовых писем на оба адреса подтверждена.
Таймер также проверен: `active/waiting`, `enabled`; последний присланный запуск
18.09.2026 15:02:40 MSK завершился с `Result=success`, `ExecMainStatus=0`.
Последующая проверка БД показала `pending_mail: 0`, `mail_with_errors: 0`.
Разработчик сообщил, что в просмотренном письме REG.RU нет `Authentication-Results`
и у него есть только ящики REG.RU. Внешняя доставка и результаты SPF/DKIM/DMARC
не подтверждены; отсутствие заголовка само по себе не доказывает сбой.
Присланный затем исходник теста на ящик сайта также не содержит `DKIM-Signature`:
отправитель и получатель — один ящик домена, видимый маршрут — mail1.hosting.reg.ru
→ sm38.hosting.reg.ru. Это не доказывает, что внешние письма остаются неподписанными;
нужно сверить настройку DKIM у почтовой услуги. Названный пользователем Roundcube
Webmail 1.6.17 — интерфейс чтения писем; панель управления услугой ещё не определена.
Позднее разработчик открыл DNSadmin и подтвердил, что единственный домен там —
`dari-sinergii.ru`. Из неё затем прислал значение DKIM TXT с RSA-ключом и прежнее
значение DMARC. OpenSSL прочитал публичный ключ без ошибок: RSA 2048 бит, DER 294 байта.
Артефакт — `artifacts/readiness/dkim-key-supplied.json`. Затем получено точное имя
`dkim._domainkey.dari-sinergii.ru.`; Google и Cloudflare независимо вернули TXT
с тем же ключом. Артефакт публикации — `artifacts/readiness/dkim-public-dns.json`.
Публикация ключа подтверждена; включение подписи у SMTP-сервера и проверка подписи
внешним получателем пока не подтверждены. Существующую запись пересоздавать не требуется.
Скриншот Roundcube подтвердил тестовое письмо во «Входящих» ящика сайта;
папка в личном ящике отдельно не подтверждалась. Сам агент к SMTP не подключался
и письма не отправлял. Уведомления о заказах через очередь требуют отдельной приёмки.
Оформление и оплату оставляем выключенными.

## Что настраивается в админке

После миграции и `setup_roles` откройте **Заказы → Почтовые уведомления → Адреса уведомлений о заказах**:

- **Email менеджера** — куда поступают уведомления о заказах. Можно менять без перезапуска и выпуска кода. Если пусто, используется прежний `MANAGER_EMAIL` из окружения.
- **Email для ответов покупателей** — существующий рабочий ящик для вопросов по заказу. Если не заполнен, используется `EMAIL_REPLY_TO`, затем адрес менеджера, затем отправителя.

Раздел доступен суперпользователю и роли «Менеджер магазина». Контент-редактор доступа не имеет. Эта роль не получает право включать оформление, менять юридические тексты магазина или SMTP-секреты.

При сохранении нового адреса ожидающие письма менеджеру становятся доступны для ближайшего запуска очереди. Перед отправкой служба выбирает актуальный адрес; письма покупателям сохраняют своих получателей. Уже отправленные письма повторно не отправляются. Если сообщение по этому событию уже есть для нового адреса, дубликат помечается пропущенным, а не отправленным. Письмо, которое SMTP уже принял в момент изменения настройки, отозвать невозможно.

Покупатель получает состав заказа с сохранёнными ценами, итог, способ получения и контакт для ответа. Ссылка на заказ по-прежнему доступна только в браузере оформления — наличие номера заказа не открывает чужие данные. Менеджер получает ссылку на заказ в админке. Письма содержат HTML и текстовую версию; внешние изображения и отслеживающие пиксели не используются.

События: заказ создан, оплата подтверждена, в обработке, готов к выдаче / передан в доставку, завершён, отменён, подтверждённый полный или частичный возврат. Письма о возвратах содержат сумму конкретного возврата и общий подтверждённый возврат на момент события. Ожидающий или отклонённый возврат не объявляется выполненным. Подключение этих уведомлений не включает ЮKassa.

## Почтовый сервис

Провайдер — REG.RU. Для его стандартной доменной почты документация указывает
`mail.hosting.reg.ru`, порт `465`, SSL и полный адрес ящика как логин.
Сверить с конкретной услугой в личном кабинете: не заменять уже работающие
параметры другим продуктом REG.RU по одному только примеру.
[Документация REG.RU](https://help.reg.ru/support/hosting/nastroyka-pochty-regru/nastroyka-pochty-i-pochtovykh-kliyentovv/nastroyka-pochtovykh-kliyentovv).

Публичная проверка DNS 18.09.2026: NS `ns5/ns6.hosting.reg.ru`, MX
`mx1/mx2.hosting.reg.ru`, одна SPF-запись с `_spf.hosting.reg.ru`, DMARC `p=none`.
SPF также разрешает IP `31.31.197.73`: принадлежность и необходимость этого
разрешения сверить с текущей почтовой услугой, не удалять без проверки.
Повторная публичная проверка NS/MX/SPF/DMARC дала прежние значения;
результат — `artifacts/readiness/dns-mail-readiness.json`.
Наличие записей не доказывает доставку или DKIM. Проверить `Authentication-Results`
реального письма: SPF, DKIM, DMARC и соответствие домену отправителя.
В используемом разработчиком `webmail.hosting.reg.ru` открыть полученное тестовое
письмо, нажать три точки в верхней панели → «Исходный текст», затем найти
`Authentication-Results` через Ctrl+F. Передать только фактические результаты
`spf=`, `dkim=`, `dmarc=`; отсутствие заголовка отметить отдельно, без вывода о сбое.
[Инструкция REG.RU по просмотру заголовков](https://help.reg.ru/support/hosting/nastroyka-pochty-regru/problemyy/kak-posmotret-pochtovyye-zagolovkii).
Если `Authentication-Results` отсутствует, следующий доступный шаг — найти
`DKIM-Signature` и взять только параметры `d=` (домен подписи) и `s=` (селектор).
По ним можно проверить опубликованный DNS-ключ. Наличие подписи и ключа само по себе
не заменяет проверку подписи сообщения и результат приёма внешним сервисом.
Если подписи в этом письме нет, сверить настройки конкретной почтовой услуги
REG.RU; не делать вывод, что нужно менять Django или включать свой SMTP на VPS.
Отсутствие `Authentication-Results` не позволяет определить валидность письма:
[RFC 8601, приложение B.1](https://www.rfc-editor.org/rfc/rfc8601.html#appendix-B.1).
DKIM-selector берётся из кабинета / `DKIM-Signature`, не угадывается.
В TXT-записи ключа `s=email` означает тип сервиса, а не селектор;
имя для DNS-проверки берётся из отдельного поля «Имя» записи:
[RFC 6376, разделы 3.6.1–3.6.2](https://www.rfc-editor.org/rfc/rfc6376.html#section-3.6.1).
Для проверки настройки почтового домена открыть личный кабинет REG.RU, выбрать
услугу, где создан почтовый ящик, затем для хостинга «Управление → Войти в панель».
Определить панель (ispmanager/Plesk/cPanel либо другой интерфейс конкретной услуги)
перед применением инструкции. Roundcube не заменяет панель настройки DKIM.
Источники: [вход в панель услуги](https://help.reg.ru/support/hosting/dostupy-i-podklyucheniye-panel-upravleniya-ftp-ssh/kak-voyti-v-panel-upravleniya-hostingom),
[настройка DKIM у REG.RU](https://help.reg.ru/support/hosting/nastroyka-pochty-regru/nastroyka-pochty-i-pochtovykh-kliyentovv/kak-nastroit-dkim-i-dmarc-dlya-pochty-regru).
У этого домена NS — ns5/ns6.hosting.reg.ru; публикацию ключа проверять именно
в действующей зоне, не менять NS/MX и не переносить почту на VPS по общему примеру.
Путь к просмотру уже найденной зоны: [инструкция REG.RU для DNSadmin](https://help.reg.ru/support/klassicheskie-vps/osnovi-raboty-s-vps/upravleniye-resursnymi-zapisyami-na-servere-vps).
`p=none` наблюдает, но не требует отклонять подделки; ужесточать DMARC после
инвентаризации всех отправителей и успешных проверок, а не вслепую.

## Подключение на VPS

1. Выпустить подготовленный код на VPS и применить миграцию `orders/0002_order_notifications`. Повторить `manage.py setup_roles`, чтобы существующие менеджеры получили права на новый раздел. При штатном выпуске `deploy/release.sh` эти действия уже выполняются. Миграция сохраняет очередь и различает старые письма покупателям и менеджеру.
2. Заполнить оба адреса в админке. `reply_to_email` должен вести в реально проверяемый ящик.
3. Через VS Code Remote SSH открыть **существующий** `/etc/dari/dari.env` и изменить только почтовые настройки. Не заменять весь файл и не переносить секрет в Git или чат. Пример после проверки домена:

```ini
EMAIL_BACKEND=django.core.mail.backends.smtp.EmailBackend
EMAIL_HOST=mail.hosting.reg.ru
EMAIL_PORT=465
EMAIL_USE_TLS=false
EMAIL_USE_SSL=true
EMAIL_TIMEOUT=15
EMAIL_HOST_USER=ПОЛНЫЙ_АДРЕС_СУЩЕСТВУЮЩЕГО_ЯЩИКА
EMAIL_HOST_PASSWORD=ПАРОЛЬ_ЭТОГО_ЯЩИКА
DEFAULT_FROM_EMAIL="Дары Синергии <orders@dari-sinergii.ru>"
```

`orders@dari-sinergii.ru` здесь только пример: использовать фактический разрешённый
адрес отправителя. Для ответа используется адрес из админки. Если для вашей услуги
документирован STARTTLS на 587, использовать `EMAIL_USE_TLS=true`, `EMAIL_USE_SSL=false`.

4. Выполнить на VPS под root проверку настроек, **без отправки**:

```bash
systemd-run --quiet --wait --pipe --collect \
  --uid=dari --gid=www-data -p SupplementaryGroups=dari \
  --working-directory=/srv/dari/current \
  -p EnvironmentFile=/etc/dari/dari.env \
  /srv/dari/current/.venv/bin/python manage.py send_notifications --check
```

Проверка не выводит пароль, не соединяется с SMTP и не изменяет очередь. Она не доказывает доставку.

5. Для реального проверочного письма на **свой** ящик использовать ту же оболочку `systemd-run`, заменив последнюю строку на:

```bash
  /srv/dari/current/.venv/bin/python manage.py sendtestemail YOUR_OWN_EMAIL
```

Заменить `YOUR_OWN_EMAIL` своим адресом. Эта команда действительно отправляет письмо; заказ не создаёт и очередь не обрабатывает. Проверить входящие/спам, отправителя и результаты SPF/DKIM/DMARC в заголовках. Проверить отправку ответа по выбранному рабочему адресу отдельно. Сообщение `sendtestemail` стандартное; макеты заказов проверены локально на синтетических данных.

Без дополнительных флагов `sendtestemail` отправляет только явно указанным
получателям. Автоматической копии менеджеру, отправителю или на почту сайта нет.
Для проверки собственного ящика сайта повторить команду с его фактическим адресом.
Успешный тест SMTP сам по себе не проверяет создание и обработку уведомлений о заказах.

6. На уже настроенном VPS после успешной доставки проверить состояние таймера и
последнего запуска службы. Следующие команды только читают состояние:

```bash
systemctl show dari-notifications.timer --no-pager \
  -p ActiveState -p SubState -p UnitFileState -p LastTriggerUSec
systemctl show dari-notifications.service --no-pager \
  -p Result -p ExecMainStatus -p ExecMainExitTimestamp
```

Ожидаются активный и включённый таймер, недавний запуск и успешный результат службы.
Один `Result=success` без подтверждения недавнего запуска не доказывает работу.
В админке проверить очередь и актуальные адреса менеджера/ответов. Успешный запуск
с пустой очередью ещё не подтверждает доставку именно уведомления о заказе.
Кроме того, команда сохраняет ошибки отдельных отправок для повторной попытки
и может завершиться с кодом 0 при наличии таких ошибок. Следующая проверка читает
только счётчики очереди, не выводит получателей и не отправляет письма:

```bash
systemd-run --quiet --wait --pipe --collect \
  --uid=dari --gid=www-data -p SupplementaryGroups=dari \
  --working-directory=/srv/dari/current \
  -p EnvironmentFile=/etc/dari/dari.env \
  /srv/dari/current/.venv/bin/python manage.py shell -c '
from orders.models import Notification
pending = Notification.objects.filter(sent_at__isnull=True, skipped_at__isnull=True)
print("pending_mail:", pending.count())
print("mail_with_errors:", pending.exclude(last_error="").count())
'
```

При выключенном оформлении и отсутствии старых писем ожидаются оба счётчика 0.
Если есть записи, изучить их состояние в админке до ручного запуска отправки.

При первоначальном подключении, когда таймер ещё не включён, после проверки
содержимого очереди использовать команды ниже. Они могут отправить ожидающие письма;
на VPS с уже работающим таймером повторять их ради диагностики не нужно:

```bash
systemctl restart dari.service
systemctl start dari-notifications.service
systemctl enable --now dari-notifications.timer
journalctl -u dari-notifications.service -n 20 --no-pager
systemctl list-timers --all dari-notifications.timer
```

Служба читает EnvironmentFile при каждом запуске. Перезапуск приложения нужен для изменённых серверных fallback-настроек; изменение адресов в админке перезапуска не требует.

## Очередь и проверка

В разделе «Email-уведомления» видны аудитория, получатель, время принятия письма SMTP, число попыток, следующая попытка и класс ошибки. SMTP-сбой не отменяет заказ или подтверждённую оплату. Повторы идут с интервалами 1, 2, 4, 8 минут и далее до одного часа. Записи с будущей попыткой не занимают текущую порцию очереди. SMTP ограничен таймаутом; во время отправки блокируется запись очереди, а не заказ.

Принятие письма SMTP не гарантирует попадание во входящие. Для отклонений после принятия нужны журналы почтового сервиса. Обычный SMTP также не даёт гарантии ровно одной доставки при обрыве после принятия письма; стабильный Message-ID не заменяет эту гарантию.

Тесты: `python manage.py test --settings=config.settings_test`. Они используют отдельную БД и почту в памяти. Локальные образцы писем: `.scratch/order-email/customer.html`, `manager.html` и соответствующие `.eml`; это синтетический заказ, письма из этих тестов не отправлялись. Отдельные SMTP-тесты с VPS доставлены на личный ящик разработчика и почту сайта. Таймер включён, последний запуск успешен; очередь пуста, записей с ошибками нет. Почтовая аутентификация, адреса менеджера/ответов и полный сценарий уведомлений о заказах ещё требуют приёмки.
