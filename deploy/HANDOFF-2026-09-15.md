## Текущее состояние

- VPS REG.RU: `134.0.113.203`, Ubuntu 24.04, 2 vCPU / 2 ГБ RAM / 30 ГБ NVMe; добавлен swap 2 ГБ.
- Стек: Python 3.12, PostgreSQL 16, Gunicorn, Nginx 1.24; Node.js 22 для сборки.
- Релиз: `/srv/dari/releases/first`, исходный коммит `d013ec2`; `/srv/dari/current` указывает на него. Исправления прав уже применены на VPS вручную, но checkout релиза сам по себе не обновлялся.
- Адреса: `https://dari-sinergii.ru/`, `https://shop.dari-sinergii.ru/`; админка — `https://shop.dari-sinergii.ru/admin/`. Суперпользователь создан пользователем.
- База и роль PostgreSQL — `dari`. Миграции, импорт исходных текстов/PDF, роли и `collectstatic` выполнены. Локальную SQLite-базу не переносили: пользователь подтвердил отсутствие собственных правок.
- Затем пользователь загрузил 16 демотоваров штатным seeder через отдельный management-процесс с временным `override_settings(DEBUG=True)`. Настройки веб-службы не менялись: `DEBUG=False`, оформление заказов и ЮKassa выключены. Повторный импорт сейчас не нужен.

## Исправленные ошибки

1. Доступ к PostgreSQL падал с «service file not found», хотя файл существовал: процесс с `Group=www-data` не проходил в `/etc/dari` (`root:dari`, `0750`). В службы и transient-команды добавлен `SupplementaryGroups=dari`; права секретов не расширялись.
2. HTML работал, но CSS/JS/картинки возвращали 403: `/srv/dari` имел группу `dari`. Исправлено на `dari:www-data`, `0750`. Это закреплено в `bootstrap.sh` и `release.sh`; после релиза проверяется также загрузка CSS через Nginx.

На VPS оба `/health/` дали `{"status":"ok"}`, страницы сайта/магазина/входа в админку — 200, `www` — 301. Из сети ассистента после исправления прав проверены CSS, JS, логотип и CSS админки магазина: 200 и правильные MIME-типы. Пользователь подтвердил восстановление оформления.

## С чего продолжить

1. **Разобраться с основным доменом в браузере пользователя.** На VPS HTML содержит «Магазин» в обычном и мобильном меню; подпись `nav_shop` заполнена. В браузере пункт отсутствует, а `/health/` возвращает `404 nginx`. Из сети ассистента основной домен/`www` также отдавали другой сертификат. Вероятен старый маршрут/DNS-кэш VPN; окончательная причина не подтверждена. VPN пользователь отключать не может. Предложено временно добавить три имени с IP VPS в Windows `hosts`, очистить DNS-кэш и перезапустить браузер; выполнение и результат **не подтверждены**. После нормализации DNS временную запись удалить. Не добавлять дублирующий пункт меню вслепую.
2. Проверить лендинг и магазин в браузере: меню, мобильную версию, видео (не отключать), изображения, документы, корзину и админку. HTTP 200 сам по себе не подтверждает корректный интерфейс.
3. Сделать свежую копию после демоимпорта, проверить архивы, восстановление в отдельную БД, срок хранения и автоматические внешние копии.
4. Завершить защиту сервера: UFW последний раз был `inactive`; проверить SSH-ключи/смену первичных паролей, доступность только нужных портов и ограничения PostgreSQL. Не менять SSH-доступ без проверки работающего способа входа.
5. Перед продажами заменить демоданные реальными товарами, согласовать цены/остатки/доставку/документы, подключить SMTP и ЮKassa, протестировать заказы и оплату. Включение `dari-reconcile.timer` и `dari-notifications.timer` ещё не подтверждено. Не включать продажи с демотоварами.

Изменения в GitHub не обновляют VPS автоматически. GitHub Actions публикует отдельную статическую демонстрацию Pages; Django-релиз развёртывается отдельно. Одноразовые помощники `/root/setup-dari-*.sh` и другие файлы `/root` создавались пользователем на VPS и не находятся в репозитории. Штатный процесс описан в [README.md](README.md).
