## Диагностика сейчас

Скопировать `deploy/audit-vps.sh` из этого проекта на VPS через Remote Explorer,
например в `/tmp/dari-audit-vps.sh`. Это диагностический файл без секретов.
В терминале уже открытого SSH-подключения:

```bash
sudo env SYSTEMD_PAGER=cat SYSTEMD_COLORS=0 bash /tmp/dari-audit-vps.sh
```

Скрипт выводит состояние служб, портов, firewall, политики SSH, права файлов,
версии пакетов и результаты Django/SMTP-проверок. Не выводит пароли, ключи,
содержимое окружения, заказы, покупателей или журналы. Не отправляет почту,
не обновляет сервер и не меняет SSH/firewall. `systemd-run` создаёт временные
диагностические процессы с окружением действующего приложения.

Если старая версия скрипта остановилась на `lines 1–14` или `(END)`, это просмотрщик
вывода systemctl. Нажать `q`: скрипт продолжится. Команда выше отключает этот
просмотрщик и для уже скопированной старой версии; локальный скрипт также исправлен.

## Подготовленный выпуск

Текущий каталог на VPS подтверждён разработчиком:
`/srv/dari/releases/email-76d6352`; Node.js `v22.23.2` соответствует требованию
`release.sh`. Разработчик выполнил следующие команды и подтвердил успешное
завершение свежей резервной копии (`Result=success`, `ExecMainStatus=0`):

```bash
sudo systemctl start dari-backup.service
sudo systemctl show dari-backup.service --no-pager -p Result -p ExecMainStatus
```

Ожидаются `Result=success` и `ExecMainStatus=0`. При ошибке не переходить к выпуску.
Успех службы ещё не заменяет проверку контрольных сумм и пробное восстановление.

Архив исходников можно подготовить локально без commit/push:

```powershell
.venv/Scripts/python.exe scripts/package-release.py dari-readiness-20260918
```

Результат — `artifacts/releases/dari-readiness-20260918.tar.gz` и файл `.sha256`
рядом. Состав задаётся списком отслеживаемых исходников и явным перечнем новых
файлов в скрипте; локальные секреты, БД, резервные копии, заполненный паспорт
доступов и инструменты агента не включаются. Shell-скрипты упаковываются с LF.
В архиве есть `RELEASE-MANIFEST.json` с базовым commit и хешами файлов, а также
`SHA256SUMS`. Это снимок рабочей копии с локальными исправлениями, а не чистый
архив базового commit. Скрипт проверяет содержимое созданного архива; существующий
архив не перезаписывает. Новые изменения требуют нового имени выпуска.

### Загрузка подготовленного архива

В новом окне **локального PowerShell Windows**, а не в терминале VPS:

```powershell
Set-Location -LiteralPath 'C:\Users\Admin\Desktop\ПРИНТ\Desktop\НЕ УДАЛЯТЬ\Dari-sinergii'
scp .\artifacts\releases\dari-readiness-20260918.tar.gz .\artifacts\releases\dari-readiness-20260918.tar.gz.sha256 root@134.0.113.203:/root/
```

Ввести пароль VPS при запросе. Затем в уже открытом **терминале VPS**:

```bash
cd /root
sha256sum -c dari-readiness-20260918.tar.gz.sha256
```

Ожидается `dari-readiness-20260918.tar.gz: OK`. При ошибке не распаковывать
и не запускать выпуск. Передача этих файлов сама по себе сайт не обновляет.
Архив сохраняет документацию на момент сборки; более поздние подтверждения
серверных шагов записываются в рабочую копию отчёта отдельно от архива.

### Выпуск после проверки загрузки

Загрузка и проверка суммы подтверждены. Конкретные команды установки этого архива,
предварительное сравнение конфигураций и откат к `email-76d6352` приведены в
[INSTALL-READINESS-20260918.md](INSTALL-READINESS-20260918.md).

1. Сохранить изменения как отдельный проверенный релиз с Pillow 12.3.0 и новыми
   файлами `core/seo.py`, `scripts/audit-public-site.py`; новые документы также включить
   в передачу. Commit/push не выполнялись; разработчик выпустил архив на VPS.
2. Проверить свежую резервную копию и способ отката. Новых миграций в исправлениях нет.
3. Значения индексации по умолчанию в новом коде соответствуют выбранному режиму.
   Их можно явно закрепить в существующем `/etc/dari/dari.env`:

   ```ini
   SITE_INDEXING_ENABLED=true
   SHOP_INDEXING_ENABLED=false
   ```

   Сохранить `CHECKOUT_ENABLED=false`, `YOOKASSA_ENABLED=false`, текущие SMTP-секреты
   и все прочие действующие значения. Не заменять файл окружения шаблоном.
4. По подтверждённой проверке HTTPS всех поддоменов сначала установить небольшой
   `HSTS_SECONDS=300`, проверить, затем увеличить до согласованного срока.
   В проекте `includeSubDomains=true`: проверить также используемые поддомены
   почты/панелей либо отдельно изменить эту политику. Сейчас публичный HSTS отсутствует.
5. Выпустить подготовленный каталог через штатный `deploy/release.sh` после
   согласования выпуска. Этот скрипт запускает таймеры уведомлений и резервных копий:
   заранее проверить очередь писем, чтобы не отправить старые сообщения неожиданно.
   Таймер сверки платежей теперь сохраняет существующее состояние: релиз его не
   включает и не выключает. В присланном списке таймеров VPS он отсутствует.
6. Повторить диагностику, тест публичных страниц и проверить:
   - главная и материалы доступны поиску, sitemap основного домена заполнен;
   - демомагазин: `X-Robots-Tag: noindex, nofollow`, HTML `noindex`, пустой sitemap;
   - PDF: `Content-Security-Policy: default-src 'none'; sandbox`;
   - вход в админку, загрузка разрешённой картинки и предпросмотр PDF;
   - после пяти неверных входов ограничивается один клиент, другие IP не блокируются;
   - корзина работает, оформление и оплата остаются выключенными.

## Для полной передачи

Внешнее резервное хранилище, срок хранения, мониторинг, аварийный контакт и
проверка восстановления требуют выбранных клиентом сервисов и ответственных.
Локальный `backup.sh` создаёт копии на том же VPS и не реализует внешнюю репликацию
или очистку старых архивов: без контроля место на диске может закончиться.

Поисковые кабинеты настраиваются под аккаунтами клиента по
[SEO-SETUP.md](../docs/SEO-SETUP.md); передача доступов — по
[CLIENT-ACCESS.template.md](../docs/CLIENT-ACCESS.template.md).
